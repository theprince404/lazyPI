## Overview

**sudo-lazy** is a tiny Raspberry Pi Pico W project that automates the most sophisticated task in a Linux administrator's life: typing a command into a terminal.

The Pico emulates a USB keyboard and types the following command:

```bash
sudo apt update && sudo apt full-upgrade && sudo apt autoclean
```

That's it. No complex framework, no cloud infrastructure, no artificial intelligence. Just a microcontroller, a USB connection, and an impressive commitment to avoiding approximately five seconds of manual labor.

Why type a command yourself when a programmable microcontroller can do it for you?

The project also demonstrates a broader security concern: **USB devices that emulate human input can interact with a computer without requiring a conventional software installation.**

## Features

- **USB keyboard emulation** — The Pico presents itself as a Human Interface Device (HID).
- **Automated command input** — Types a predefined Linux package-maintenance command.
- **Minimal implementation** — One small project for one gloriously unnecessary task.
- **Hardware-based automation** — Sends input through USB rather than running a conventional application on the target computer.
- **Security awareness** — Demonstrates why trusting physical peripherals can introduce security risks.

## The Application

The purpose of this project is to automate a command that a Linux user could easily type themselves.

| Command | Purpose |
|---|---|
| `sudo apt update` | Refreshes the local APT package indexes. |
| `sudo apt full-upgrade` | Upgrades installed packages and may install or remove packages to resolve dependency changes. |
| `sudo apt autoclean` | Removes obsolete package files from the local APT cache. |

The `&&` operators ensure that each subsequent command runs only if the preceding command succeeds.

### Why?

Because laziness is not a bug. It is a design philosophy.

The Pico does not need to understand Linux, know what a package is, or comprehend the consequences of upgrading an operating system. It simply types what it has been told to type.

Naturally, the command still requires appropriate authorization. The Pico does not magically acquire root privileges, bypass `sudo`, or guarantee that an upgrade will complete.

It just types. Very enthusiastically.

## The Security Issue: USB HID Input Injection

### 1. What Is USB HID?

USB Human Interface Device (HID) is a standard for peripherals such as keyboards and mice.

When a USB keyboard connects to a computer, the operating system identifies the device through its USB descriptors and loads the appropriate driver. The keyboard can then send input reports representing key presses and releases.

Microcontrollers capable of USB device emulation can implement the same interface. A Raspberry Pi Pico W can therefore be programmed to behave like a keyboard and send predefined keystrokes to a connected host.

From the host operating system's perspective, the input may be indistinguishable from input generated by a physical keyboard.

This functionality is legitimate and widely used for accessibility, embedded interfaces, automated testing, and hardware control.

It also creates a security concern when a computer accepts input from an untrusted device.

### 2. The Trust Boundary

The fundamental issue is not that USB is inherently vulnerable. It is **implicit trust in physical input devices**.

A typical desktop environment accepts keyboard input from connected HID devices without requiring the user to approve every keystroke. This behavior is necessary for ordinary computer use, but it can also allow a malicious or compromised peripheral to inject input.

A programmable device may attempt to:

- Open a terminal or interact with an already-open application.
- Enter commands or text.
- Trigger keyboard shortcuts.
- Interact with applications using the privileges of the active user session.

The impact depends on the operating system, desktop environment, screen-lock state, active window, device policies, and other security controls.

A USB keyboard emulator does not inherently exploit memory corruption, defeat operating-system authentication, or gain administrator privileges. It takes advantage of the host's willingness to accept keyboard input.

### 3. Why Can This Be Dangerous?

Consider a workstation where an unauthorized person can connect a programmable USB device.

If the workstation is unlocked, the desktop accepts keyboard input, and a terminal can be opened, an input-injection device may be able to enter commands in the context of the logged-in user.

If those commands invoke privileged operations, additional authorization may still be required.

For example, `sudo` normally requires the user to be authorized for the requested operation. Depending on its configuration and cached authentication state, it may also require a password.

The security impact can increase when:

- The user is logged in with an unlocked session.
- The user has administrative privileges.
- Privileged authentication is already cached or configured for passwordless execution.
- The device is connected to a machine with weak physical-access controls.
- The user executes injected commands without inspecting them.

A locked screen, restricted USB device policy, limited user permissions, or other controls may prevent or reduce the impact.

**The important distinction:** USB HID input injection is a technique for delivering input. It is not, by itself, proof of a vulnerability that permits privilege escalation.

### 4. Is This a USB Vulnerability?

More precisely, this demonstration illustrates a potential attack vector arising from the interaction between USB device trust, human-interface input, and the security configuration of the host.

It is commonly associated with *BadUSB-style attacks* and *HID injection*, although these terms are not interchangeable in every context.

BadUSB is a broader class of threats involving malicious USB device behavior, including devices that impersonate different peripheral types or abuse device firmware trust.

HID injection is narrower: a device emulates a keyboard or another input peripheral to deliver input to the host.

The security weakness is contextual. A computer behaving as designed by accepting keyboard input is not necessarily defective. The risk emerges when an attacker can introduce untrusted input into a privileged or sensitive workflow.

### 5. How to Mitigate the Risk

Organizations and individual users can reduce exposure through layered controls:

- **Physical security:** Prevent unauthorized access to USB ports and unattended workstations.
- **Session locking:** Lock the desktop whenever leaving the computer unattended.
- **Least privilege:** Avoid running everyday sessions with unnecessary administrative permissions.
- **USB device control:** Use operating-system or endpoint-management policies to restrict unauthorized peripherals where practical.
- **Authentication hygiene:** Review `sudoers` rules, passwordless privileges, and authentication caching.
- **Command review:** Never execute unexpected commands merely because they appear in a terminal.
- **Monitoring:** Where appropriate, use endpoint monitoring and device-control mechanisms to identify suspicious peripheral activity.

USB device restrictions must be implemented carefully because keyboards, accessibility devices, and other legitimate peripherals may be affected.

No single mitigation guarantees protection against every USB-based attack.

## Demonstration and Intended Use

This project is intended for educational use, personal automation, and authorized security demonstrations.

Test it only on computers you own or have explicit permission to assess.

The demonstration assumes that the connected computer accepts the Pico's keyboard input and that the relevant user interface is available. It does not guarantee that the terminal opens, that the command executes, or that administrative authentication succeeds.

Because the command can upgrade packages and potentially remove packages as part of dependency resolution, review its effects before allowing it to run on an important system.

## Hardware

- Raspberry Pi Pico W
- USB data cable
- Linux computer for the intended demonstration

The Pico W's wireless capabilities are not required for basic USB keyboard emulation. This project uses the board's USB device functionality.

## Usage

1. Build and flash the firmware using the project's existing instructions.
2. Connect the Pico W to a computer you are authorized to test.
3. Ensure the target is in an appropriate, controlled test environment.
4. Observe the keyboard input and verify the resulting behavior.

The exact firmware setup and build commands depend on the implementation included in this repository.

## Limitations

This is a deliberately small proof of concept, not a general-purpose USB attack framework.

It does not inherently:

- Bypass the login screen.
- Defeat `sudo` authentication.
- Grant root privileges.
- Exploit a kernel vulnerability.
- Guarantee successful command execution.
- Provide stealth, persistence, or remote access.

Its purpose is to demonstrate how a simple hardware device can automate keyboard input and why the security of the receiving computer matters.
